1KEYFORGE PRO

A single-file mobile web app that turns a bitting code into a key you can see, zoom, print and cut. This case study covers what the app does, how it is built, and the geometry audit that made the key on screen, the STL file and the DXF drawing one and the same shape.

01 — Project Overview & Core Goals

OVERVIEW & CORE GOALS

1KeyForge Pro designs a key from its bitting code. Pick one of eight profiles, set a cut value for each pin and the key redraws at true scale: the outline, a milled V-cut at every pin, the key-ring hole and a code badge. From there the same shape exports as an SVG, an STL for 3D printing or a DXF for CNC and laser.

Four goals shaped the build.

01
Instant

Every slider move redraws the key straight away: under 0.1 ms per redraw, measured in headless Chromium.

02
True to scale

One SVG unit is one millimetre. All eight profiles draw at the same pixels per millimetre, so a 71 mm key looks longer than a 54 mm one.

03
One shape

The preview and all three exports are derived from a single outline, so they cannot disagree with each other.

04
Self-contained

One HTML file of about 49 KB. No framework, no build step, no libraries and no network requests.

02 — Tech Stack & Architecture Highlights

TECH STACK & ARCHITECTURE

No framework and no build step. The app is plain JavaScript and inline SVG in one HTML file, so it can live on any static host and opens straight from a file. The interesting decision is how the code is divided: a key database, one geometry engine, and thin layers that draw, move and export what the engine produces.

Input
KEY_TYPESEight profiles: dimensions, pin count, cut range, tip shape, presets.
bittingOne number per pin, for example 3 2 5 1 4. Written by the sliders, presets and saved cuts.
→
Geometry engine · pure functions · mm
keyContour(k, bits)One closed outline per key.
  • A polygon with a fillet radius at each corner.
  • The V-cuts are its vertices, taken from the lower envelope of every cut profile.
  • Arcs stay arcs. Counter-clockwise, no self-contact.
→
Outputs
buildPath()SVG path with true arcs. Drives the live preview and the SVG export.
buildSTL()Arcs flattened to 0.02 mm, ear-clipped, written as a binary STL.
buildDXF()One closed polyline with arc bulges, plus the key-ring circle. Millimetres.
render scene built once per key type view zoom and pan as a CSS transform export Blob downloads
One outline, many outputs

keyContour() builds the outline once. Every cut is a trapezoid and the top edge of the blade is the lowest of all of them, so neighbouring cuts can never overlap or leave a sliver. SVG, STL and DXF are all derived from the result.

True arcs where they matter

SVG and DXF keep arcs as arcs. Only the STL flattens them, to a 0.02 mm tolerance, because a mesh cannot hold a curve. The path in the SVG matches the polygon in the STL to an IoU above 0.998 on all eight profiles.

Build the scene once

Gradients, clip path, milling grooves and pin labels are created once per key type. Moving a slider only rewrites the path data and the label values, so nothing is torn down while you drag.

Zoom without re-rendering

Pinch, drag, Ctrl/⌘ + wheel and double-tap reset all run through Pointer Events and one CSS transform. The pan is clamped so at least 48 px of the key always stays on screen.

03 — Key Features & Interactive Elements

FEATURES & INTERACTION

Four tabs under a live preview. The controls sit in the lower part of the screen and the key gets the rest; a collapse tab on the edge of the preview hides the controls and gives the key the whole screen.

01 / 04

Bitting

Move a slider and the key redraws, with a milled V-cut at every pin.

  • Live key. Outline, cut depths and the bitting code update as you drag.
  • One slider per pin. Four to six, depending on the profile, with the cut value under each.
  • Calibration scale. 0.5× to 3.0× for matching the drawing to a real key. Pinch or Ctrl/⌘ + wheel to zoom, drag to pan, double-tap to reset.
  • Code badge. The bitting, as you would read it off a key.
02 / 04

Key Type

Pick a profile and every dimension follows.

  • Eight profiles. Schlage SC1 and SC4, Kwikset KW1, Weiser WR3, Yale Y1, Master No.3, Best A and Arrow AR1.
  • Specs on the card. Pin count, length, code and cut range, for example 6 pins · 71 mm · cuts 1–7.
  • One true scale. Every profile renders at the same pixels per millimetre, so lengths compare honestly.
03 / 04

Presets

Start from a factory bitting, or save your own.

  • Factory presets. Each profile carries one to four of its own.
  • Saved cuts. Auto-numbered per profile (KW1-01, KW1-02). Tap one to load it back onto the key.
  • Save current bitting. One tap stores the sliders as they are. The list lives in memory for the session.
04 / 04

Export

Take the key into a drawing, a slicer or a CNC.

  • SVG. True-size vector, in millimetres.
  • STL. A watertight solid for 3D printing, with the key-ring hole cut through.
  • DXF. One closed outline plus the key-ring circle, for CNC and laser.
  • Copy bitting code. Puts the code on the clipboard. File names carry the profile and the bitting, for example KW1_65656.stl.
04 — Key Design & Engineering Challenges Overcome

CHALLENGES OVERCOME

The original build (v4) looked right at a glance. To find out whether it was, the audit measured it the way a maker would: in millimetres, at the seams, with the exports opened in code instead of trusted. What follows compares v4 with the refactor (v5) on the same keys and the same bittings.

4.1

Six defects, one cause

Zoomed in, the original outline had six problems. They shared a root cause: the bow and the blade were separate sub-paths, the cuts were an effect added afterwards, and nothing guaranteed the pieces fitted. The fix was structural. v5 describes the key once, as a single closed outline, and everything else is derived from it.

1
Hook below the blade

The bow dips 0.37 mm under the blade’s bottom edge, right at the collar.

2
Seam at the collar

Bow and blade are two sub-paths, so a stroke shows where they meet.

3
Highlight outside the key

The edge highlight is shifted 0.4 mm and was never clipped to the silhouette.

4
Tip crosses itself

On SC1 and SC4 the outline self-intersects in 36 of 36 test bittings.

5
No key-ring hole

The bow was a plain slab, so the key could not hang from a ring.

6
Cuts as soft bumps

Cosine curves instead of milled V-cuts, and the lowest cut value drew no cut at all.

Cuts that look milled

Straight 45° flanks and a flat 0.8 mm root, the way a cutter leaves them. The shallowest cut sits 0.45 mm below the blade top so every pin position has a seat, and a deep cut’s flank steepens automatically if it would reach into the next pin.

Metal that stays inside the lines

A vertical gradient from highlight to shadow, milling grooves, and an edge highlight nudged 0.4 mm down. All of it is clipped to the outline, so nothing can leak past an edge.

A code you can read

Each pin gets its number above its cut value, centred over the pin and tied to the blade by a tick, so the code reads in the same order as the cuts.

4.2

What you see is what you print

The original STL exporter rebuilt a simplified bow and fanned the face out from a single corner. The printed face and the key on screen disagreed by 34.1 mm² (5.0%), seven edges were shared by more than two triangles, and the volume came out negative: the solid was inside-out. v5 cuts the face from the same outline the screen draws. The key-ring hole is joined to the outline with a bridge, ears are clipped, and every vertex is kept so the side walls and the faces share them.

The trap in ear clipping

The first version of the new triangulator dropped collinear vertices, which left a crack against the side wall on about 6% of bittings. It now keeps every vertex and emits a zero-area facet rather than a hole, and the audit counts open edges on every bitting.

4.3

Same key, same scale

In v4 every profile fitted its own viewBox, so on a phone the scale ran from 4.94 to 5.99 px per millimetre depending on the key, a spread of 19.3%. v5 uses one fixed 76 × 25 mm window, the longest key plus a margin, so all eight profiles render at the same scale: 5.13 px/mm on a 390 px phone and 9.47 px/mm from 768 px up. The same change fixed the zoom. At 3× the original showed about 37% of the key and could not pan. v5 keeps the pinch and adds drag-to-pan, Ctrl/⌘ + wheel zoom and a double-tap reset, with a clamped pan, and every key fits fully inside the preview at 1×.

4.4

Exports built for real tools

The original DXF held 144 separate LINE entities: no bow, no closed contour and no units. v5 writes one closed polyline with true arc bulges, the key-ring hole as a circle, millimetres declared in the header and the origin at the blade shoulder. The SVG export is true size, with width and height in millimetres on a 1:1 viewBox (v4 exported at a fixed 10 px per millimetre, with 4 mm of margin at the sides, 10 mm above the bow and 7 to 9 mm below the blade).

4.5

Proving it

Every claim above was checked by code that shares none of the app’s logic: shapely for the outline, trimesh for the mesh, ezdxf for the drawing and Playwright for the behaviour in the browser.

What this does not claim

Performance was never the problem. A redraw fell from about 0.35 ms to about 0.1 ms, but both are far below a frame; the gain is that dragging no longer rebuilds the whole scene. The key dimensions are working approximations of common profiles, not manufacturer drawings, and the exports were validated with libraries rather than in a physical slicer or on a CNC.

05 — Future Enhancements / Roadmap

WHAT’S NEXT

Ideas, in rough order. The limits they address are real ones in the current build.

Next
Installable and offline

Add a web manifest and a service worker. Today the app has the iOS home-screen tags but no manifest and no offline cache, so it is a web app rather than a full PWA.

Next
Keep and share

Saved cuts live in memory and vanish on reload. Persist them in localStorage and add share links such as ?k=SC1&b=32514 and a paste-a-code import.

Next
Say what is approximate

Mark every profile as an approximation in the interface and record where each dimension comes from in the key database, instead of a comment that implies a standard.

Then
Accessibility pass

The viewport disables browser zoom (user-scalable=no). Move to in-app zoom only where needed, check contrast of the orange labels, and add a reduced-motion path.

Then
Audit in CI

The geometry audit and the browser checks run as scripts today. Put them in a CI job so a geometry regression fails the build.

Then
Undo and redo

Step back through slider changes and preset loads, with a short history that survives a profile switch.

Idea
Engraved label

Deboss the profile code and bitting on the bow of the STL so printed samples can be identified.

Idea
Finishes and dark mode

Brass, nickel and anodised looks on the same geometry, and a dark interface that matches the system setting.

06 — Outcome

SAME APP, SOUNDER FOUNDATION

The interface keeps the original’s tabs, sliders, presets and key database. What changed is underneath. One outline now drives the screen, the SVG, the STL and the DXF; all eight profiles draw at the same scale; the exports pass independent checks; and the app is still one 49 KB page with no dependencies.

Accuracy and use

The profile dimensions are working approximations of common key shapes and have not been checked against manufacturer drawings. 1KeyForge Pro is for visualising, learning and prototyping.

It is not a way to copy a key you do not own or are not authorised to duplicate.
